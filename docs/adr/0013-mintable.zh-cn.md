# 0013 可增发：部署后的发行是模块，初始发行和销毁属于核心

- 状态：Accepted（owner，2026-10-15；在 A.1 0.7.0 与 B.1 0.3.0 中实现）
- 日期：2026-10-15
- 范围：家族（修订 [ADR-0008](0008-modules.zh-cn.md) 第 5、6 条，以及 [07](../07-family-conventions.zh-cn.md) §3、§5、§7、§13、§14）

## 背景

到 A.1 0.6.0 和 B.1 0.2.0 为止，每个代币都通过**角色铸造**模块发行：持有 `MINTER_ROLE` 的人调用 `mint(to, amount)`，持有人可以按公开金额销毁。除此之外没有别的东西能产生供应。核心只搬动已有的余额，公开账本只在公开余额和机密余额之间互换，Wrapper 端口只能放回从它出去的量。所以 07 §13.2 需要一条规则：「一个组合至少有一个供应来源」，不含角色铸造的组合都是空代币。dApp 的模块模拟器把这一点摆了出来：A.1 的八种模块子集里有四种根本不是代币。

owner 看了这个模块实际给了什么（2026-10-15）。它给的不是「一个能铸造的角色」，而是**部署之后继续发行的权利**。没有它的代币，初始发行量以后不能增加，这正是多数发币平台提供的、持有人也依赖的性质。有它的代币是某些业务需要的：发行方持续增发，或者一个合约凭它持有的东西铸造，比如锁在里面的已有 ERC-20。

由此带出两件小事。

- **销毁。** 这个模块还带着持有人的销毁（`0x81`）。普通 ERC-20 的销毁可有可无：ERC-20 标准里没有，`ERC20Burnable` 才加上；多数项目是把代币转到黑洞地址，代币统计网站会把它从流通量里排除。隐私代币里这样做不行。机密转账给一个没人控制的 id，金额是隐藏的，谁也没法排除它。只有公开金额的销毁才是别人能核对的减少供应的方式，而每个代币，不论只发行一次还是持续增发，都可能需要它。
- **托管发行。** 07 §13.1 为「锁定普通 ERC-20、发行隐私代币的金库」保留了「托管发行」这个名字，ADR-0008 第 5 条把它设想成一个有自己限额的端口。发行既然是一个角色，金库就只是一个持有该角色的合约；它的出口是 Wrapper 端口已经有的那个。

## 决定

1. **角色铸造模块改名为可增发。** 英文 Mintable，代码 id `mintable`，接口 `ICasataMintable`。接口只有一个函数 `mint(address,uint256)`，所以 ERC-165 id 仍是 `0x40c10f19`，按旧名部署的代币会被识别为有这个模块。`MINTER_ROLE` 不改名。这个模块只增加 `mint`。

2. **初始发行属于核心。** 每个代币在部署时确定初始发行量和接收方。
   - 接收方遵循 `mint` 的规则（07 §3）：有公开账本且不带发行类型时是公开账户，否则由 Variant 的发行类型决定（A.1：机密 id；B.1：一个 note）。
   - Variant 怎么完成初始发行由它自己定，只要只发生一次、并且是部署的一部分。A.1 在构造函数里记入。B.1 的铸造需要证明（B.1 01-design D6），它的文档说明这个证明怎么交给构造函数。
   - 只有带可增发的代币，初始发行量才可以是零。不带可增发、又什么都没发行的代币永远不可能有余额，所以部署会回滚。
   - 它和任何发行一样，发出从零地址开始的 `Transfer` 和 Variant 的发行事件（A.1、B.1：`Minted`）（07 §7）。空代币回滚用的错误名由 Variant 定（A.1：`NoSupply()`）。

3. **持有人的销毁属于核心。** 每个代币都允许持有人凭自己的证明销毁自己余额里的一笔公开金额：`transferFrom(from, 0x0, amount)` 加 Variant 的销毁类型（A.1 和 B.1 都是 `0x81`）。不需要角色。它复用核心已有的出口，不需要新电路。

4. **供应规则改变。** 「一个组合至少有一个供应来源」改为：每个代币在部署时发行初始供应；可增发是唯一能在部署后发行的模块；端口放回的量不超过从它出去的量。这样，一个 Variant 声明的模块的任意子集都有供应，07 §13.2 的「任意子集」不需要第二条规则就成立。Variant 自己的其他规则仍可能排除某个子集（A.1 到 0.6.0 为止：公开账本和 Wrapper 端口同时存在，见 [A1-0007](a1-0007-exit-kind-binding.zh-cn.md)）。

5. **撤回「托管发行」这个保留的模块名。** 锁定已有 ERC-20 并据此发行隐私代币，由家族的**网关**完成（[14](../14-gateway.zh-cn.md)）。网关是一个运行时合约，代币通过两个已有的模块接入它：
   - 可增发：网关持有 `MINTER_ROLE`，收到多少就铸多少。
   - Wrapper 端口：网关是代币的 `wrapper()`。它的出口是 `wrapperBurn`，证明里绑定收款人，网关把锁定的 ERC-20 放给这个收款人。

   代币对网关的限额只有总量上限，因为锁定的资产不在代币里。供应有没有足额抵押，取决于网关和角色：网关必须是 `MINTER_ROLE` 的唯一持有者，管理员必须放弃授予该角色的权利，初始发行量必须为零。前端把这样的代币称为有抵押之前，要先检查这几点（14 §4）。

6. **版本。** 核心变了，所以每个 Variant 都要出一个声明可增发的新版本：A.1 0.7.0 和 B.1 0.3.0。旧版本保留各自声明的列表，同一个模块在里面叫角色铸造；旧版本的代币不变。

## 备选方案

- **保留「角色铸造」这个名字。** owner 否决：它说的是谁来铸，不是这个模块给了什么，还会让「不发行」读成「没有代币」。
- **一个固定供应模块**，在部署时发行一次，与角色铸造并列。2026-10-15 提出，当天撤回：初始发行是每个代币都有的，属于核心；为它设一个模块，「不选模块」就没有意义了。
- **销毁留在可增发里。** owner 否决：只发行一次的代币也可能要销毁，而在隐私代币里，销毁是唯一能公开地减少供应的方式。
- **一个有自己限额的托管发行端口**（ADR-0008 第 5 条）。否决：这会是第三个端口、第四个接口，做的是一个角色加一个已有端口就能做的事；而且锁定的资产在别处，代币本来也检查不了它的限额。
- **一个存入端口**，方向与 Wrapper 端口相反。2026-10-15 提出，当天以同样的理由撤回。

## 影响

- 正面：一个 Variant 的模块的任意子集都是代币，只有核心就是一个固定供应的隐私代币。固定供应免去了持有人对发行方的信任。
- 正面：模块名录变短（少一个保留名），它保留的场景由已有模块覆盖。
- 正面：每个代币都能以任何人都可核对的方式减少供应。
- 负面：两个 Variant 的核心都要改。两者都需要新版本、对构造函数和销毁的复审、新的测试网部署，以及 dApp 的改动（模块名、模拟器、部署表单）。
- 负面：由网关抵押的代币，可靠程度取决于它的角色设置。代币不强制抵押，所以集成方必须检查角色持有者（第 5 条）。
- 负面：B.1 的部署更重，因为初始发行要带一个证明。
