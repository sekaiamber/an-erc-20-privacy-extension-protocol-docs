# 0010 ERC-20 兼容逐项取舍；转账仍是共用的动词

- 状态：Accepted（2026-10-13；同日已在约定、合约和 dApp 里实现，即 A.1 0.6.0 和 B.1 0.2.0；测试网上的三个代币尚未重新部署）
- 日期：2026-10-13
- 范围：家族（修订 [ADR-0003](0003-erc20-surface-conventions.zh-cn.md) 第 1、6、7 条；影响 [07](../07-family-conventions.zh-cn.md) §1、§5、§6、§7、§13.1，[A1-0006](a1-0006-fold-and-received-block.zh-cn.md) 里折叠的入口，以及 [A.1 模块规范](../tracks/track-a/variant-1/04-modules.zh-cn.md)的决定 M1）

## 背景

ADR-0003 只有一个目标：让现有钱包与合约无需新 ABI 就能触达机密功能。做法是复用 `transfer` / `transferFrom`，把 payload 附在参数后面，并让每个代币都带完整的 ERC-20 表面。

现在已经部署了三种代币，ERC-20 表面在它们身上的含义各不相同：

| 代币 | `balanceOf` | 不带 payload 的 `transfer` | `approve` |
| --- | --- | --- | --- |
| A.1 带公开账本 | 真实余额 | 真实转账 | 真实授权 |
| A.1 纯隐私 | 对所有人都是 0 | 回退 | 返回 true，什么都没授权 |
| B.1 | 只有代币自身地址有余额 | 回退 | 返回 true，什么都没授权 |

当初的目标后来怎么样了：

- 没有哪个钱包会生成证明或拼 payload。到目前为止，每一次机密操作都是本项目的 dApp 或脚本发出的。
- 不了解本协议的合约调用 `transferFrom` 时，在它以为是金额的位置拿到的是句柄。
- 为这类调用方准备的兜底路径（先 `prepare`，再裸调用），dApp 没有用过，B.1 没有做，而它在 A.1 安全评审里占了四条发现和两条拒绝服务条目（F2、F3、F4、F10、D3、D6）。

复用确实带来的东西，是 2026-10-13 在 BscScan 测试网上对 A.1 纯隐私代币观察到的：

- 一笔机密转账被显示为一笔普通的 BEP-20 转账，从 `A` 到 `id(B)`，句柄被显示成一个约七十位的金额（[交易](https://testnet.bscscan.com/tx/0x5578642b080f4b831e35dc7ec8f2181cd668fd4ede8f1b81e766dd2b279d2c62)）。
- 代币被识别为 BEP-20，总供应量（750）和转账笔数（5）都正确。持有人为 0，持有人榜是空的，没有被句柄算出来的余额填满。

owner 的立场（2026-10-13）：对 ERC-20 的兼容既不全盘放弃，也不能不计代价。它要逐项权衡：便利性、实现代价、是否让设计更有吸引力。其中转账应当在整个家族里保持为同一种行为、同一个事件。

## 决策

1. **每一项用三个问题来定。**

   | 问题 | 答案是否定时 |
   | --- | --- |
   | 代币给出的回答是真的吗？ | 不提供。返回假结果的函数比没有这个函数更糟 |
   | 便宜吗？ | 要看第三问 |
   | 有人用吗？或者它让设计更容易讲清楚吗？ | 不为它专门搭一套机制 |

   回答为真，并且要么不花成本，要么便宜且有人用或有故事可讲，这一项就保留。

2. **转账是家族与 ERC-20 共用的唯一动词。** 凡是移动价值的操作，都走 `transfer` / `transferFrom`，涉及机密一侧时带尾部 payload，并发出标准的 `Transfer` 事件。

   | 操作 | 调用 | `Transfer` 事件 |
   | --- | --- | --- |
   | 机密到机密 | `transferFrom(from, to, handle)` 加 payload | `(from, to, handle)` |
   | 公开到机密（公开账本模块） | `transfer(to, amount)` 加 payload | `(from, token, amount)` |
   | 机密到公开（公开账本模块） | `transferFrom(from, to, amount)` 加 payload | `(token, to, amount)` |
   | 按公开金额销毁 | `transferFrom(from, 0x0, amount)` 加 payload | 去往零地址 |
   | Track B | 同样的调用；没有账户可指的地方填代币自身的地址 | `(token, token, handle)`，或来自 / 去往零地址 |

   发行是一笔来自零地址的转账，有自己的入口（第 10 条）。Wrapper 端口保留它的函数。两者都照现在的做法发出来自和去往零地址的 `Transfer`。

3. **句柄继续放在金额槽里**（ADR-0003 第 5 条，不变）。区块浏览器会把它显示成一个很大的金额。这一点接受：它读起来就是「这个金额不公开」，而转账本身仍然被列出来。

4. **尾部 payload 继续作为家族的扩展机制**（ADR-0003 第 2 条，不变），并明确它用在哪里：

   - 签名由别人规定的函数，payload 附在参数后面。这包括 ERC-20 的函数，以及家族模块接口里各 Track 共用的函数。
   - Variant 自己定义的函数，把 `bytes payload` 作为普通参数。
   - 不带 payload 的调用，行为与标准函数完全一致。

5. **不移动价值的操作不使用转账动词。** A.1 的折叠（`0x80`）是一种整理操作，ERC-20 里没有对应的东西，改为独立的函数。它的签名，包括是否保留句柄，在 A.1 规范里确定。

6. **读取表面在所有代币上保留**：`name`、`symbol`、`decimals`、`totalSupply`、`balanceOf`。它们在每个代币上都是真的。没有公开账本的代币上，`balanceOf` 报告的是公开余额，对用户来说就是零。

7. **没有公开账本的代币上，`approve` 回退** `NoPublicLedger()`，`allowance` 返回 0。现在的 `approve` 返回 true 却什么都没授权，这是假回答。

8. **撤销兜底路径**（ADR-0003 第 7 条）。`prepare` 和 `cancel` 从家族约定里移除。Variant 不必实现它们，新的 Variant 不实现，A.1 在下一个版本里删除。

9. **客户端在签名前说明句柄。** 在请钱包对一笔带句柄的调用签名之前，界面要说明：钱包会显示一个很大的数，它是句柄，不是金额。

10. **发行使用 `mint(address to, uint256 amount)`，规则与转账相同。** ERC-20 没有规定铸造函数；它只说创建代币时应当发出来自零地址的 `Transfer`，这一点家族的每个代币都已经做到。`mint(address,uint256)` 是现有工具认识的签名，所以家族采用它，并由 payload 决定 `to` 的含义：

    | 调用 | 含义 |
    | --- | --- |
    | 不带 payload 的 `mint(to, amount)` | 向地址 `to` 公开发行。没有公开账本的代币上回退 `NoPublicLedger()` |
    | `mint(id, amount)` 加 payload | 把一笔公开金额发行给机密 id（Track A） |
    | `mint(token, amount)` 加 payload | 把一笔公开金额发行成 note；note 的所有者在 payload 里（Track B） |

    它取代 `mintConfidential`。这与 A.1 在决定 M1 之前的做法不同：那时 `mint` 的含义取决于代币是哪一种组合；现在取决于 payload，和转账一样。接口 `IPEPRoleIssuance` 及其 ERC-165 标识随之改变。

11. **供应量的呈现是推荐，不是强制。** 代币应当给出足以让任何人算出机密供应量的数字：`totalSupply()` 等于在该代币上已发行且未销毁的数量，从中减去公开部分即可。Variant 怎么呈现由它自己决定，包括是否像 B.1 那样让代币自身地址在 `balanceOf` 里持有机密供应量。代币能否隐藏自己的供应量，本 ADR 不作决定；目前没有 Variant 这样做。

本 ADR 之后 ADR-0003 仍然成立的部分：第 2、3、4、5 条不变。第 1 条对转账仍然成立：转账不新增选择器。第 6 条改读作「凡是移动价值的操作都发出标准 `Transfer`」。

## 备选方案

- **ADR-0003 原样不动。** 被否决：`approve` 会继续给出假回答；兜底路径会继续为一个从未出现的调用方消耗评审精力。
- **把所有机密操作都改成独立函数，不再为它们使用 ERC-20 的选择器。** 这是最先提出的方案，被 owner 否决：标准事件才是现有工具接触代币的地方；共用转账动词的代价实际上很小；浏览器里的显示效果可以接受。
- **用 `transferFrom(0x0, to, amount)` 发行**，让铸造在字面上也使用转账动词。被否决：由某个角色授权、从零地址发起的 `transferFrom` 不是任何读者预期的东西；会铸造的工具调用的是 `mint(address,uint256)`。
- **在公开的 `mint` 之外保留 `mintConfidential`**（A.1 的决定 M1）。被第 10 条取代：一个函数，由 payload 决定含义，和转账一样。
- **机密转账的标准 `Transfer` 事件金额填 0。** 被否决：区块浏览器和钱包把零金额的代币转账当作地址投毒，默认隐藏。
- **在没有公开账本的代币上去掉 `balanceOf`。** 被否决：它的回答是真的，不花成本，而且浏览器靠它识别代币。

## 后果

- 正面：家族有了一条规则来回答下一个兼容性问题，而不是一句笼统的承诺。
- 正面：转账在每个 Track 里都是同一种行为、同一个事件，现有的区块浏览器继续列出机密转账。
- 正面：A.1 去掉了预登记的状态、三个函数和它们的事件，也去掉了随之而来的一类评审发现。
- 负面：把 `Transfer` 的数值加总的工具会把句柄当成金额。BscScan 不会；其它索引器没有验证过。
- 负面：钱包在签名时把句柄显示成金额。第 9 条只是我们自己客户端里的缓解措施，对别的客户端不起作用。
- 负面：在带公开账本的代币上，向机密 id 铸造时如果漏了 payload，会产生一笔没有人能控制的公开余额。转账本来就遵循这条规则（ADR-0003 第 4 条），现在它也适用于铸造方。
- 负面：仍然不支持 ERC-2771 的转发器，与 ADR-0003 相同。
