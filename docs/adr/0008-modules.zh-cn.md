# 0008 Track、Variant 与模块：公开账本是模块，不是 Track

- 状态：Accepted（结构已定；合约尚未重构，见「过渡」；「过渡」由 [0009](0009-track-b-notes.zh-cn.md) 更新）
- 日期：2026-10-12
- 范围：家族（修订 [ADR-0002](0002-track-variant-structure.zh-cn.md) 第 1–4 条、[ADR-0007](0007-track-definition.zh-cn.md) 第 2、3 条，以及 [ADR-0005](0005-family-wrapper.zh-cn.md) 的措辞）

## 背景

Track A 与 Track B 是按一个问题分开的：代币有没有公开账本。三件事说明这一刀切错了位置。

- **这种分法过不了 ADR-0007 的第一项检验。** B.1 没有自己的电路，它的合约引用 A.1 的验证器接口和曲线库，跑在同样的三个电路上（transfer、unshield、fold）。两个合约之间的差别，不动电路就能在同一个 Track 内做到。
- **公开账本和 Wrapper 端口踩的是同一对底层动作。** 一个是按公开金额记入机密账户，不需要证明（退化密文 `(amount·G, 0)`）。另一个是凭 unshield 证明按公开金额扣出，证明里绑定金额和公开收款地址。A.1 的 `0x03` / `0x04` 与 B.1 的 `wrapperMint` / `wrapperBurn` 是这对动作的两个使用方。
- **同一个选项在每条路线里都会出现。** 预演 note 模型时，「有没有公开账本」又作为它内部的一个选项出现。每个 Track 里都有的选项，不可能是区分 Track 的东西。

把这个选项放进编号也行不通。当作 Variant 序号，它会错位：带公开账本的形态在一个 Track 里是 A.2，在另一个里是 B.3。当作后缀，每多一个各 Track 共有的属性就多一个后缀。

## 决策

1. **三层结构。**

   | 层 | 是什么 | 换一个的代价 |
   | --- | --- | --- |
   | **Track** | 状态模型与信任基础 | 每个家族工具都要适配；按 ADR-0007 写家族级 ADR |
   | **Variant** | 一套电路：密码学内核，以及它隐藏了什么 | 新的验证器、新的可信设置、新的安全评审 |
   | **模块** | 合约层的选配，原样复用该 Variant 的电路 | 只改合约 |

   功能（ADR-0007）仍然指不需要改合约的东西。

2. **每个 Variant 的基底是纯隐私账本；公开账本是模块。**

   - Track A 重新定义为**加密账户**：每个账户一份同态密文余额，密钥由用户持有，证明在客户端生成，不依赖外部网络。
   - 原 Track B 撤销。已发布的两个合约是同一个 Variant（A.1）的两种组合。
   - 字母 B 释放，重新适用 ADR-0007 第 4 条。

3. **两种模块。**

   | 种类 | 怎么接入代币 | 什么时候用 |
   | --- | --- | --- |
   | **编译时模块** | 继承进代币合约，字节码随之变化 | 要读写机密状态、改变已有函数的行为，或是每笔操作都要经过的小检查 |
   | **运行时模块** | 外部合约，插在一个**端口**上；端口本身是一个很小的编译时模块 | 自带状态、体积大、只需要端口，或可以全家族只写一份 |

   需要改电路的是 Variant，不是模块。监管密文是在 transfer 电路里强制的，所以「要不要监管」不是模块。监管密钥由谁持有（单方或委员会）是部署参数。

4. **运行时模块的规则。**

   - **只走端口。** 运行时模块通过普通调用到达，绝不在代币的存储里运行。
   - **部署时定死，或只能设置一次。** 之后不能安装或卸载。事后加进来的模块可以凭端口铸造，这等于一条升级通道。
   - **代币不信任模块。** 每个端口都带一个由代币强制的限额。B.1 的 `wrappedOut` 是第一个这样的限额：Wrapper 最多只能记回从它这里出去的数量。
   - **不设通用钩子。** 代币在转账前后不对外回调。金额是密文，钩子只看得到 id；而能让转账失败的钩子等于冻结权，[07 §9](../07-family-conventions.zh-cn.md) 已排除。

5. **模块登记。** 模块在 [07 §13](../07-family-conventions.zh-cn.md) 里登记，全家族一份；实现由各 Variant 自己写。Variant 要写明它支持哪些模块；不支持的模块就是不实现，探针也不会报告。

   **2026-10-13 更新（owner）。** 声明以版本为单位：每个 Variant 的每个版本都要声明一份封闭的、它所支持的模块清单。以后新登记的模块，已有版本的清单不变；要支持新模块，就得给该 Variant 出新版本。规则写在 [07 §13.2](../07-family-conventions.zh-cn.md)。

   | 模块 | 种类 | 增加了什么 | 现状 |
   | --- | --- | --- | --- |
   | 公开账本 | 编译时 | 代币地址上的标准 ERC-20 余额；`0x03` shield 与 `0x04` unshield；`shieldedSupply()` | 在 `ConfidentialERC20A1` 里 |
   | 角色铸造 | 编译时 | `MINTER_ROLE` 按公开金额 `mint`：有公开账本时铸到公开账本，否则铸到机密账户，并提供 `0x81` 销毁 | 两个合约里都有 |
   | Wrapper 端口 | 端口加运行时模块 | `IPEPWrappable`，由家族的 `PEPWrapper` 使用；限额为 `wrappedOut` | 在 `ConfidentialERC20B1` 里 |
   | 托管发行 | 端口加运行时模块 | 锁定普通 ERC-20、发行隐私代币的金库 | 未设计，搁置 |

   Wrapper 与托管金库可以共用端口接口，因为两者都是按公开金额记入、凭证明按公开金额扣出。它们不能共用限额：Wrapper 只能归还出去过的数量，金库则按锁定的资产发行。所以限额属于端口，不属于接口。

6. **编译时模块的组合。**

   - 继承顺序全家族固定：内核、公开账本、发行、端口。两个模块重写同一个内部函数时，叠加方式因此总是一样的。
   - 一种组合至少要有一个供应来源。
   - 公开账本与 Wrapper 端口可以共存，因为两者用的是同一对底层动作。目前看不到这种组合的用途，所以不做。

7. **探针。** 在 ERC-165 之外，代币通过一个 view 报告自己的模块。

   ```solidity
   interface IPEPModules {
       struct Module { bytes4 id; address at; }
       /// `at == address(this)`：已编译进代币。其它非零地址：插在该端口上的运行时模块。
       /// 零地址：端口存在，但没有插任何模块。
       function pepModules() external view returns (Module[] memory);
   }
   ```

   `id` 是该模块接口的 ERC-165 接口标识，`supportsInterface(id)` 对它返回 true。与 `pep()` 一样，这份清单是自我声明。前端按 `pep()` 决定进哪个页面，按模块决定开哪些功能。合约重构之前，这个接口只是草案。

8. **编号与版本。**

   - Variant 序号表示它在所属 Track 内的开设顺序。不同 Track 的序号没有对应关系。
   - 组合没有编号，也没有后缀，用它的模块来描述。
   - `pep()` 的格式 `"<track>:<variant>:<version>"` 不变。一个版本号覆盖一个 Variant 的内核及其编译时模块。运行时模块有自己的版本号。

9. **保持不变的部分。** Variant 之间仍然互不依赖：代码在一个 Variant 内部共享，或通过家族的运行时模块共享，不在 Variant 之间共享。ADR-0002 第 5 条继续有效。

10. **ADR-0007 的第一项检验增加一个分句。** 如果一条路线的核心性质可以在既有 Track 内靠新增一个 payload 类型、替换一个电路、增加一条客户端约定，**或者加上、去掉一个模块**做到，它就是可替代的。

## 过渡

从现在起，文档按上面的结构描述。代码还没有跟上。

| 现状 | 在新结构里 |
| --- | --- |
| `ConfidentialERC20A1`，`pep()` = `A:1:0.4.0` | A.1，带公开账本和角色铸造 |
| `ConfidentialERC20B1`，`pep()` = `B:1:0.2.0` | A.1，纯隐私，带角色铸造和 Wrapper 端口 |

- 合约重构之前，「B.1」仍然是第二个合约的名字，它的文档仍在 `docs/tracks/track-b/variant-1/` 下。部署记录与安全评审编号（`B1-F1` 等）永久保留原名。
- 重构是单独的一步，需要 owner 另行同意：合约拆成共享内核加模块，统一为一个版本号，两个测试网代币以 `A:1:…` 重新部署，dApp 改为按模块路由，两个文档目录合并。完成之后字母 B 才空出来。
- **2026-10-13 更新（[ADR-0009](0009-track-b-notes.zh-cn.md)）。** 字母 B 已在重构之前分配给 note 模型。第二个合约的文档移到了 `docs/tracks/track-a/variant-1-privacy-only/`。在重构之前，该合约保留原名和 `B:1:…` 描述符，在那之前也不会部署任何 note 模型的代币。

## 备选方案

- **继续按公开账本区分 Track A 与 B。** 被否决：这种分法过不了 ADR-0007 的第一项检验，而且以后每开一个 Track 都要在里面再分一次。
- **把每种形态编成一个 Variant，用对照表比较。** 被否决：相同形态的序号在不同 Track 之间会错位。
- **每个共有属性加一个后缀**（`A.1L`）。被否决：每多一个共有属性，所有名字都要多一个后缀。
- **只用运行时模块，基底字节码只有一份。** 被否决：公开账本要和代币同址，代币就得转发每一个 ERC-20 调用并替模块发事件；每新增一种端口，所有代币的基底都要出新版本。
- **只用编译时模块。** 被否决：只需要端口的大块状态（包装代币的登记表）会留在代币里，而且每个 Variant 都要重写一遍 Wrapper。
- **让模块在代币的存储里运行。** 被否决：任何一个出错的模块都能改写全部机密余额。
- **部署后可安装的模块。** 被否决：见第 4 条。

## 后果

- 正面：相同的形态不会再得到不同的编号；新发现一个各 Track 共有的属性，只是登记表里多一行、多一个接口，不需要改名；Wrapper 只写一份；代币合约保持小体积。
- 正面：A.1 与 B.1 之间已经共享的代码有了归属。它们还是两个 Track 时，这违反了 ADR-0002 第 3 条。
- 负面：集成方必须先探测。同一个 Track 的两个代币，`balanceOf` 与不带 payload 的 `transfer` 可能表现不同。「同一 Track 下的 Variant 对集成方表现一致」收窄为「同一 Track 的代币共享状态模型与信任基础」。
- 负面：编译时模块直接访问存储，相互影响比端口难推理。所以它们的数量要少，安全评审要覆盖每个模块和每种实际发布的组合。
- 负面：合约与 dApp 要重构，两个测试网代币要重新部署。0.4.0 与 0.2.0 两个版本号合并为一个。
- 体积：两个合约分别是 17,060 与 17,195 字节，上限是 24,576。包含全部模块的组合还没有测过。曲线库现在是整段编进代币的，空间不够时可以改成单独部署的链接库。
