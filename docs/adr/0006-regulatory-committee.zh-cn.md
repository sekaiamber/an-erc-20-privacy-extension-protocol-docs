# 0006 监管方改为门限委员会合约；密码内核改为普通 ElGamal

- 状态：Accepted（2026-09-28 §3 落地；2026-09-29 §1–§2 原型落地，见下文「实现修订」）
- 日期：2026-09-27
- 范围：家族（工具）；对 A.1 v0.4 / B.1 v0.2 的协议修订

## 背景

监管方目前是一把私钥。owner 要求一个合约来保管监管解密能力，成员可动态增减、审批策略可插拔（多数票；指定票 + 额外票且指定票自己不能解密），像第二个家族工具那样按项目部署。合约保不住秘密，唯一可靠的实现是门限密钥：份额在成员手里，成员、策略与审计痕迹在链上。

## 决策

1. 新增 [11-regulatory-committee](../11-regulatory-committee.zh-cn.md)：`IRegulatorCommittee`（群公钥、epoch、成员、策略、request / approve / combined），配 DKG、保持 `pk_reg` 不变的重分享、带 Chaum–Pedersen 证明的部分解密。首批实现：Shamir 多数票与两层「指定 + 额外」结构。按项目 / 团队部署，多种并存。
2. 代币不变：委员会持有代币的 `REGULATOR_ADMIN_ROLE`，其 `groupKey()` 即当前 `pk_reg`（家族约定 §9）。
3. **协议修订（已于 2026-09-28 随 A.1 0.4.0 / B.1 0.2.0 落地）**：改为普通 ElGamal——`pk = s·H`，共享 `D = r·H`，每方一个 `C_X = v·G + r·pk_X`；memo 密钥流由各方共享秘密 `r·pk_X`（= `s_X·D`）派生，删掉 `E` / `e`。目的：监管侧解密与 memo 打开都成为标量乘（可门限拆分），DKG 聚合成为点加。（初稿写作「密钥流由 `r·H` 派生」是错的：普通 ElGamal 下 `r·H` 公开。）
4. 策略结构必须与秘密分享结构一致；策略合约只与其部署时配套的分享方式一起有效。

### 实现修订（2026-09-29，原型）

- **策略 = 分组 AND，不另设策略合约。** 秘密 `s = Σ_g s_g`，每组独立 `t_g`-of-`n_g` Shamir；查看与换届投票都要求每组达到阈值。一个 `RegulatorCommittee` 合约同时覆盖多数票（一组）与「指定 + 额外」（单人组 + t-of-n 组），第 4 条自动成立。OR 结构 / 加权需 LSSS，未实现。
- **部分解密加密给请求人。** 明文部分解密一旦上链，任何人都能合成 `s·D`；改为成员用 `k·X_requester` 派生的掩码加密 `[P_1…P_m, c, z]`，链上只有密文事件和区块锚点。Chaum–Pedersen 证明为批量 DLEQ，由请求人链下校验。
- **份额不落地。** 份额以加密形式存在 `Dealt` 事件里，成员密钥由钱包 EIP-712 签名派生，随时可恢复。代价：被移除成员仍能重建旧届份额，旧届法定人数线下合谋仍可解密；怀疑泄露时应新建委员会并重新绑定代币。
- 份额投递、重分享（前 `t_g` 名旧成员分发、常数项等于旧公开份额）、异议即失败 + `restart`、实测 gas 与待决事项见 [11 §4–§10](../11-regulatory-committee.zh-cn.md)。

## 备选方案

- 保留单密钥、放进多签控制的保管库（MPC 托管服务）：把信任转移给托管方，且链上没有查看审计；否。
- 对*每个*成员各加密一份（每笔 n 份密文）：任一成员即可解密，没有门限；payload 随 n 增长；否。
- 门限 FHE / 重加密网络：为同样的结果动用更重的机器；超出范围。

## 后果

- 正面：监管访问没有单点失守；增减成员不必轮换密钥；每次查看都有链上记录；策略可换。
- 负面：多两个家族合约和一套 DKG / 重分享客户端；A.1 多一次电路修订（不过电路会变小：−1 次标量乘、−2 个公开输入、−64 字节 payload）。
- 单密钥模式仍然有效（成员数为一的委员会）；dapp 监管视图（`/tools/regulator`）同时支持单密钥与委员会两种模式。
