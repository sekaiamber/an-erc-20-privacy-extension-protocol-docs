## 0. B.1 是什么

B.1 是 note 模型的第一个 Variant。价值存放在 **note** 里。创建一张 note，就是把它的承诺加进链上的一棵 Merkle 树；花掉一张 note，就是公开它的作废符。链上没有账户、没有 id、没有余额。

能复用 A.1 的地方都复用：Baby Jubjub、Poseidon、Groth16、由钱包签名派生的密钥、在共享的 `D = r·H` 下加密的 memo，以及监管密钥接口。

| | A.1 | B.1 |
| --- | --- | --- |
| 价值存在哪里 | 每个账户 id 一份密文余额 | note：树里的承诺 |
| 链上的收款方 | 稳定的 id `Poseidon(pk)` | 没有 |
| 链上的付款方 | 稳定的 id | 没有（提交交易的地址可见，见 §12） |
| 收两次款 | 两笔转给同一个 id 的转账 | 两条互不相干的承诺 |
| 花钱时有人打款进来 | 需要 `pending` 和折叠 | 互不影响：证明引用的是某个树根 |
| 电路 | transfer、unshield、fold | 只有一个：join-split |
| 钱包怎么找到自己的钱 | 读自己的账户槽和自己的事件 | 对该代币的每笔交易逐条试解密 |
| 监管视图 | 按账户，用 id 过滤事件 | 一个区块区间内的全部交易 |

## 1. 设计原则

1. **链上只存承诺和作废符，不存任何关于用户的东西。** 没有公钥，没有 id，没有按用户划分的存储槽。
2. **只有一个电路。** 转账、铸造、销毁和经 Wrapper 的进出是同一个命题，只是公开金额不同。
3. **每笔交易长得一样。** 不管实际有几个输入和输出，总是公开两个作废符和两条承诺。
4. **证明即授权。** 花费由「知道所有者密钥」的证明授权，任何人都可以提交交易。
5. **监管在电路里强制。** 如果监管 memo 没有如实写出真实的输入、输出的真实所有者和金额，这笔交易就证不出来。
6. **证明不会过期。** 证明引用的是某个树根，而所有历史树根都一直有效。

## 3. note

### 3.1 收款码

收款码就是公钥 `pk`，64 字节，由收款人在链下交给付款人。它是稳定的、可以重复使用的，因为它从不出现在链上：每次向它付款，都会用一个新的 `ρ` 生成一条承诺；同一把公钥名下的两条承诺，除了所有者和监管方，谁也关联不起来。

没有注册，也没有开户。

### 3.2 承诺与作废符

- 承诺隐藏了金额和所有者。`ρ` 让它每次都不一样。
- 作废符里包含叶子位置。如果付款人用相同的 `(v, pk, ρ)` 创建了两张 note，它们位于不同位置，作废符不同，所以两张都能花。
- 没有 `s` 就算不出一张 note 的作废符，所以没有人能看出一个公开的作废符对应哪一条承诺。

### 3.3 树与树根

- 一笔交易把它的两条承诺作为一对追加：先把这一对哈希一次，再向上哈希 31 次到树根。
- 合约用 `mapping(uint256 => bool)` 记下每一个树根，证明针对其中任何一个都有效。旧树根下已经在树里的 note 现在仍然在树里，双花由作废符集合防止，所以旧树根是安全的。
- 钱包使用最新的树根。使用旧树根会让观察者知道被花的 note 比那个树根更早。

## 4. join-split 命题

一笔交易最多花掉同一个所有者的两张 note，并创建两张 note。

```
v_in1 + v_in2 + v_pub_in  ==  v_out1 + v_out2 + v_pub_out
```

**公开输入**（逻辑列表；与 A.1 一样，标量打包成字，点只公开 `x` 和一个符号位）：`root, nf[2], cm[2], v_pub_in, v_pub_out, to, chainId, contract, regKeyId, pk_reg, D, memo_recv[2][3], memo_reg[5]`。打包后是 21 个域元素（§4.1）。

**私有输入**：`s`；每个输入的 `(v, ρ, leafIndex, path)`；每个输出的 `(v, pk, ρ, ref)`；`r`。

| # | 命题 | 说明 |
| --- | --- | --- |
| 1 | `pk_in == s·H`，且 `s < l` | 两个输入属于同一把密钥。`l` 是子群的阶。没有这个上界，`s` 和 `s + l` 就是同一张 note 的两把密钥，会算出两个不同的作废符，这张 note 可以被花两次 |
| 2 | 对每个输入：`cm_in = Poseidon(v, pk_in, ρ)` 位于 `root` 下的 `leafIndex`，**或者** `v == 0` | `v == 0` 的输入是占位输入，跳过成员检查 |
| 3 | 对每个输入：`nf == Poseidon(s, ρ, leafIndex)` | 占位输入用随机的 `ρ`，它的作废符看起来和别的没有区别 |
| 4 | 对每个输出：`cm == Poseidon(v, pk, ρ)`，且 `pk` 在曲线上 | 公钥不在素数阶子群里时，这张 note 谁也花不了；这是付款人的损失，和填错收款码一样 |
| 5 | 每个 `v`、`v_pub_in`、`v_pub_out` 都小于 `2⁶⁴` | |
| 6 | 上面的平衡等式 | |
| 7 | `D == r·H` | 两个收款方和监管方共用 |
| 8 | 对每个输出 `j`：`memo_recv[j] == Enc(r·pk_j; v_j ‖ ρ_j ‖ ref_j)` | `ref` 是付款人自由填写的字段，见 §6.1 |
| 9 | `memo_reg == Enc(r·pk_reg; 输入 ‖ 输出)` | §6.2。真实输入在 memo 里的叶子位置等于第 2 条里用的位置；占位输入则是「无」标记 |
| 10 | `to`、`chainId`、`contract`、`regKeyId` 与符号位的打包 | 把证明绑定到这个代币、这条链，以及出金时的公开收款地址 |

深度 24 时的实测规模：55,343 个约束，其中 35,429 个是非线性约束；A.1 的 transfer 是 29,719 个。最初的估计是深度 32 时 45,000 到 55,000 个。

### 4.1 公开输入与哈希的用途

验证器接收 21 个域元素，顺序如下：

| # | 输入 | 内容 |
| --- | --- | --- |
| 0 | `root` | |
| 1–2 | `nf[2]` | |
| 3–4 | `cm[2]` | |
| 5 | `w0` | `to`（160 位），然后是 `chainId`（64 位） |
| 6 | `w1` | `contract`（160 位）、`regKeyId`（32 位），然后是 `pk_reg` 和 `D` 的符号位 |
| 7 | `w2` | `v_pub_in`（64 位），然后是 `v_pub_out`（64 位） |
| 8–9 | `xs[2]` | `pk_reg` 和 `D` 的 `x` |
| 10–15 | `memo_recv[2][3]` | §6.1 |
| 16–20 | `memo_reg[5]` | §6.2 |

哈希的用途：

| 用途 | 函数 | 输入 |
| --- | --- | --- |
| 树节点 | 2 输入的 Poseidon | 左、右。空叶子是 0 |
| memo 的密钥与填充 | 2 输入的 Poseidon | §6 |
| 作废符 | 3 输入的 Poseidon | `s, ρ, leafIndex` |
| 承诺 | 4 输入的 Poseidon | `v, pk.x, pk.y, ρ` |

输入个数不同的 Poseidon 是不同的函数。树节点和 memo 填充共用 2 输入的那一个：填充从不公开，它的第二个输入是一个很小的常数，而树节点的两个子节点都是哈希输出。

## 5. ERC-20 表面

家族约定 §1–§5 适用：标准选择器、尾部 payload、金额槽里放句柄。Track B 对它们的收窄见 [Track 文档](../README.zh-cn.md)。

| 调用 | payload 类型 | 公开金额 | 含义 |
| --- | --- | --- | --- |
| `transferFrom(token, token, handle)` | `0x01` | 无 | note 之间转账 |
| `transferFrom(token, 0x0, amount)` | `0x81` | `v_pub_out = amount`，`to = 0x0` | 持有人销毁。0.3.0 起属于核心；到 0.2.0 为止属于角色铸造 |
| 构造函数，`initialSupply` 与 `initialPayload` | `0x82` | `v_pub_in = initialSupply` | 初始发行，部署时一次。0.3.0 起属于核心（§7.1） |
| `mint(token, amount)` | `0x82` | `v_pub_in = amount` | 可增发（到 0.2.0 为止叫角色铸造）；仅 `MINTER_ROLE` |
| `wrapperBurn(0x0, to, amount, payload)` | `0x81` | `v_pub_out = amount`，绑定 `to` | Wrapper 端口：出到包装代币 |
| `wrapperMint(recipient, amount)` | `0x82` | `v_pub_in = amount` | Wrapper 端口：`recipient` 就是整个 payload |
| 不带 payload 的 `transfer`、`transferFrom`、`mint` | 无 | 无 | 回退 `NoPublicLedger()` |
| `balanceOf(a)` | 无 | 无 | 代币自身地址返回 `totalSupply()`，其它地址返回 0 |
| `approve`、`allowance` | 无 | 无 | `approve` 回退 `NoPublicLedger()`；`allowance` 返回 0 |

- `token` 指代币自身的地址。note 转账里 `from` 和 `to` 不携带任何信息，所以固定为它。标准事件于是读作池子内部的一次移动，不会被当成铸造或销毁。
- 重放由作废符阻止：一份 payload 只能执行一次。
- B.1 没有 `prepare` / `cancel`。家族已经撤销了这条路径（约定 §6）。
- `mint` 就是家族可增发接口（约定 §13.1；到 0.2.0 为止叫角色铸造）里的那个函数，join-split 作为尾部 payload 附在后面，从 `msg.data[68:]` 读取。这里没有账户可指，所以 `to` 必须是代币自身的地址。不带 payload 的 `mint` 是公开发行，B.1 没有这种发行。0.1.0 里这个函数叫 `mintConfidential`。
- **payload。** 所有操作共用一种布局，838 字节：类型（1）、flags（1，必须为 0）、`root`（32）、`nf[2]`（64）、`cm[2]`（64）、`D`（64）、`memo_recv`（192）、`memo_reg`（160）、`regKeyId`（4）、证明（256）。公开金额和 `to` 是调用的参数，由证明绑定。
- **payload 类型。** `0x01` 是 note 转账；`0x81` 是公开金额流出（销毁、wrap）；`0x82` 是公开金额流入（初始发行、铸造、unwrap）。证明不绑定类型。销毁和 wrap 靠 `to` 区分：销毁时为零地址，wrap 时不为零。
- **不需要出口绑定。** A.1 0.7.0 把出口类型绑进证明的收款人值，因为同时有公开账本和 Wrapper 端口的代币有两个收款人非零的出口（[A1-0007](../../../adr/a1-0007-exit-kind-binding.zh-cn.md)）。B.1 只有一个：wrap。销毁的零收款人把另一个隔开，所以 B.1 0.3.0 照旧绑定 `to`。加入公开账本的 B.1 版本需要同样的绑定。

### 5.1 模块

### 5.2 供应量

`totalSupply()` 是池子里持有的数量：部署时发行的与铸造的，减已销毁，减当前经 Wrapper 出去的数量。`issuedSupply() = totalSupply() + wrappedOut`，上限 `2⁶⁴ − 1` 针对的是它，初始供应也计算在内。这与 A.1 纯隐私组合的记账方式相同。

## 6. memo

两种 memo 都使用由共享秘密 `r·pk_X` 派生的 Poseidon 密钥流，以输出序号和字序号作为域标签：`key = Poseidon(shared.x, shared.y)`，`pad[w] = Poseidon(key, 16·party + w)`，第 `w` 个字在域内加密为 `m + pad[w]`。两个输出的 `party` 分别是 0 和 1，监管方是 2，所以同一个共享秘密下的两份 memo（两个输出给同一把公钥）不会重复使用填充。

### 6.1 收款方 memo

每个输出三个字：`v`、`ρ`、`ref`。

- 收款方计算 `s·D`，解开 memo，重新计算承诺，与链上的承诺比较。相等就说明这张 note 是自己的。
- `ref` 是付款备注，例如订单号。收款方看不到是谁付的款，所以商户需要它把付款和订单对上。电路只负责加密它，不约束它的取值。

### 6.2 监管 memo

五个字：两个输入的叶子位置（或「无」），以及每个输出的所有者公钥和金额。

| 字 | 内容 |
| --- | --- |
| 0 | `in₀ + in₁·2³²`；真实输入的 `inᵢ` 是 `leafIndex + 1`，占位输入是 0 |
| 1、3 | 输出 0 和输出 1 的 `pk.x` |
| 2、4 | 输出 0 和输出 1 的 `v + sign(pk.y)·2⁶⁴` |

监管方据此重建全部 note 的表：所有者、金额、创建它的交易、花掉它的交易。某把公钥在任意时刻的余额，就是它名下未花 note 的总和。不需要任何人配合（ADR-0004 第 5 条）。

- **往回查可以定点。** 解开一笔交易就能看到它的输入叶子位置，而创建某个叶子的交易是公开的。追查资金来源只需要解开那些交易。
- **往后查不行。** 一张 note 后来被哪笔交易花掉是隐藏的，所以追查资金去向或计算余额，都需要解开区间内的每一笔交易。

## 7. 流程

### 7.1 发行

**铸造（可增发）。** 铸造方知道收款人的收款码。它构造一个 join-split：两个占位输入，`v_pub_in = amount`，一个输出给收款人，一个零金额输出，然后调用 `mint(token, amount)`，把 payload 附在后面。

金额虽然公开，仍然需要证明，因为监管方必须在新 note 创建的那一刻就知道它的所有者（§14 D6）。

**初始发行（核心，0.3.0 起）。** 同样的 join-split，在代币存在之前做好，由它的构造函数检查。

1. 部署者算出代币将来的地址。用 `CREATE` 部署时，地址由部署账户和部署交易的 nonce 决定。
2. 它对着空树的树根构造 join-split；空树的树根只取决于深度和哈希，事先就知道。`v_pub_in = initialSupply`；两个输出给一个或两个收款码，所以初始供应可以分给两个所有者，比如金库和团队。监管 memo 加密给构造函数将作为 key id 0 装入的监管公钥。
3. 它把 `initialSupply` 和 payload 作为构造参数部署。构造函数在建好树和监管公钥之后检查上限，执行 join-split（证明绑定 `contract` 和 `chainId`，§4.1），把这一对承诺追加到叶子 0 和 1，发出 `Transfer(0x0, token, initialSupply)`、`Minted(initialSupply)` 和第一条 `NoteTransfer`。

- **只有一次。** 这条路径只存在于构造函数里。
- **地址算错只损失 gas，不损失价值。** 如果账户先发了别的交易，nonce 变了，地址就不同，证明验不过，部署回滚。
- **不用 `CREATE2`。** 它的地址取决于 init code，init code 里会有证明，而证明又绑定地址。工厂合约可以在构造期间通过一次调用把 payload 交过去，打破这个循环；0.3.0 不需要它。
- **零。** `initialSupply = 0` 加空 payload 只在带可增发的组合上允许。不带可增发时部署回滚，因为这个代币永远不可能有余额（ADR-0013 第 2 条）。
- **实现说明。** Solidity（0.8.21 起）允许构造函数在 immutable 赋值后读取它，所以初始发行就在组合的构造函数末尾走普通的 join-split。构造参数不是 calldata，所以 payload 解析改为从内存读取；普通调用的 payload 先复制到内存，相对一次证明验证，这点 gas 可以忽略。
- **成本。** 本地实测：部署 `B1Token` 并把初始发行分给两个持有人，共 8,142,825 gas，包括合约创建和新树上的首次铸造；部署者的钱包生成一次证明，约 3 秒。合约大小：`B1Token` 11,244 字节，`B1TokenM` 14,236，`B1TokenW` 14,873，`B1NoteToken` 15,510。

### 7.2 转账

付款人的钱包挑出自己的一张或两张 note，创建收款人的 note 和给自己的找零 note，生成证明；任何人都可以带着 payload 提交 `transferFrom(token, token, handle)`。合约检查树根，检查两个作废符都没出现过，验证证明，记下作废符，追加这一对承诺，记下新树根。

### 7.3 销毁

与转账相同，只是 `v_pub_out = amount`、`to = 0x0`。找零以 note 的形式返回。0.3.0 起销毁属于核心：每个 B.1 代币的每个持有人都能销毁，不论有没有可增发。在 note 池里，这是别人能核对的唯一减少供应的方式：发给一把没人持有的公钥的 note，金额仍是隐藏的（ADR-0013「背景」）。

### 7.4 wrap 与 unwrap

- **wrap**（note 换成包装 ERC-20）：`CasataWrapper.wrap(token, 0x0, to, amount, payload)`。证明绑定 `to` 和 `amount`。`wrappedOut` 增加。
- **unwrap**（包装 ERC-20 换回 note）：`CasataWrapper.unwrap(token, recipient, amount)`，其中 `recipient` 是一份 `v_pub_in = amount` 的 join-split payload。代币检查 `amount ≤ wrappedOut`。

Wrapper 合约原样使用，不需要改动。

**经家族网关（0.3.0 起）。** 带可增发和 Wrapper 端口的 B.1 代币可以是已有 ERC-20 的隐私形态：[网关](../../../14-gateway.zh-cn.md)是它的 `wrapper()`，也是 `MINTER_ROLE` 的唯一持有者。

- **存入。** 存入者的钱包像铸造那样构造 join-split：两个占位输入，`v_pub_in = amount`，输出给它选的收款码。它把 payload 和 ERC-20 一起交给网关。网关把 payload 作为 `mint(token, amount)` 的尾部 payload 转交；放回经它出去的量时，则交给 `wrapperMint`。两条路径给证明的公开输入相同（`v_pub_in = amount`，`to = 0`），所以一份证明两条路都能用。证明绑定金额，网关没法记入别的金额。别人复制这份 payload，只能带着同样的存入提交，产生的也是同样的 note。
- **取回。** 持有人证明一个 `0x81` join-split，`v_pub_out = amount`，`to` = 收取 ERC-20 的地址。网关调用 `wrapperBurn(0x0, to, amount, payload)`，把 ERC-20 放给 `to`。
- **精度。** note 是 6 位小数，`v < 2⁶⁴`。小数位更多的 ERC-20 由网关换算（14）。

### 7.5 A.1 里会出的问题，这里不会出

- **两笔交易同时发生。** 各自引用的树根都一直有效，谁也不会让对方作废，所以没有 `pending`，也没有折叠。
- **同一张 note 花两次。** 第二笔交易发现作废符已经被记录，回退。

## 8. 事件与视图

| 事件 | 字段 | 何时发出 |
| --- | --- | --- |
| `Transfer` | `(token, token, handle)`；`(0x0, token, amount)`；`(token, 0x0, amount)` | note 转账；铸造与 unwrap；销毁与 wrap |
| `NoteTransfer` | 第一个叶子位置、新树根、`nf[2]`、`cm[2]`、`regKeyId`、`D`、两份收款方 memo、监管 memo、`v_pub_in`、`v_pub_out`、`to`、`prevBlock` | 每一次操作 |
| `Minted`、`Burned` | `amount` | 初始发行与铸造、销毁。0.3.0 起两者都由核心声明 |
| `WrapperMinted`、`WrapperBurned` | `amount`；`to` 与 `amount` | unwrap、wrap |
| `RegulatorKeyRotated` | 与 A.1 相同 | 轮换 |

`NoteTransfer` 没有任何能识别用户的索引字段。这正是目的所在，也是钱包无法过滤事件的原因（§9）。

`prevBlock` 是上一次操作所在的区块，`lastOperationBlock()` 是最近一次操作所在的区块。两者把这个代币的全部历史串成一条链：客户端从最新的区块开始往回走，每次只请求一个区块，不需要扫描中间那些什么都没有的区块。

视图：`root()`、`isKnownRoot(root)`、`isSpent(nf)`、`leafCount()`、`totalSupply()`、`issuedSupply()`、`wrappedOut()`、约定 §9 的监管密钥视图、返回 `B:1:<version>` 的 `casata()`、模块探针，以及 `TREE_DEPTH()`、`hasher()`、`verifier()`、`lastOperationBlock()`。

## 9. 客户端

- **扫描。** 钱包读取该代币的每一条 `NoteTransfer`：从 `lastOperationBlock()` 开始沿 `prevBlock` 往回走，直到遇到已经处理过的区块（§8）。每一条做一次标量乘 `s·D`，然后尝试两份收款方 memo。它没法向节点只要「自己的」事件。
- **树。** 同一遍扫描让钱包拿到每一条承诺，据此维护树的前沿和自己 note 的路径。向服务器索要某个叶子的路径，会暴露正在花的是哪张 note。
- **作废符。** 钱包算出自己 note 的作废符，一旦某个作废符出现在链上，就把对应的 note 标为已花。
- **换设备。** 用钱包签名重新派生出同一把密钥，从代币的部署区块开始重新扫描。
- **合并。** 持有很多小额 note 的钱包两张两张地合并。花掉 `N` 张 note 需要 `N − 1` 笔交易。

## 10. 情景

Alice 付款，Bob 是商户，Carol 和 Dave 是其他顾客。

| 步骤 | 用户做什么 | 链上能看到什么 |
| --- | --- | --- |
| 开户 | Bob 在钱包里签一次名，得到收款码 | 什么都没有 |
| 发行 | 发行方给 Alice 铸造 100 | 一笔 100 的铸造，两条新承诺。看不到给了谁 |
| 付款 | Alice 付给 Bob 30，备注「订单 17」 | 两个作废符、两条承诺、几段 memo。看不到谁付、付给谁、付了多少 |
| 收款 | Bob 的钱包扫描，发现一张 30 的 note，并读到「订单 17」 | 没有新增 |
| 继续收款 | Carol 付 50，Dave 付 20 | 又两笔形状相同的交易。看不出收款人是同一个 |
| 合并后付款 | Bob 把 30 和 50 合并，再用 80 和 20 付给供应商 90 | 两笔普通交易，彼此之间、与之前的收款之间都关联不上 |
| 出金 | Bob 把 10 wrap 到自己的公开地址 | 一笔 10 出到该地址。看不出来自哪些收款 |
| 监管 | 委员会批准查看某个区块区间 | 没有新增；申请人得到该区间内的所有者、金额和关联 |

## 11. 隐私评估（家族约定 §12）

| 目标 | 达成 | 说明 |
| --- | --- | --- |
| P1 金额隐藏 | 转账完全隐藏 | 铸造、销毁、wrap、unwrap 的金额公开 |
| P2 收款方 | 隐藏 | 链上没有收款方标识 |
| P3 付款方 | 账本上隐藏 | 提交交易并支付 gas 的地址可见（§12） |
| P4 交易关联 | 账本上不可关联 | 残余的关联：提交地址、时间、使用旧树根 |
| P5 划转关联 | 除金额和时间外不可关联 | 铸造 100 后很快出金 100，两者会被关联 |
| S1 不能凭空增发 | 满足 | 平衡等式加范围检查 |
| S2 不能双花 | 满足 | 作废符集合 |
| S3 不能盗取 | 满足 | 花费需要 `s` |
| S4 公开模式不受影响 | 不适用 | 代币地址上没有公开账本 |
| S5 没有冻结角色 | 满足 | 没有冻结、没收或强制转移接口 |

## 12. 成本与限制

**一笔交易的 gas。** 每种操作的成本大致相同，因为它们验证的是同一个证明，都要追加一对承诺。

*追加一对承诺，本地实测（2026-10-13，`contracts/test/track-b/variant-1/NoteTree.ts`）。* 数字包含一笔交易 21k 的基础费，以及树根、树根标记、叶子计数这三次存储写入。

| 深度 | 可容纳的交易数 | circomlibjs 的 Poseidon | 手工优化的 Poseidon |
| --- | --- | --- | --- |
| 20 | 50 万 | 794k | 588k |
| 24 | 800 万 | 943k | 696k |
| 32 | 20 亿 | 1,243k | 912k |

- 用 circomlibjs 生成的 Poseidon 合约，每一层约 37k gas；用手工优化的实现，每一层约 27k。
- 对一棵全新的树做第一次追加要多花一些，只有一次，花在前沿的首次写入上：深度 24 时约多 42 万，深度 32 时约多 55 万。
- 手工优化那一列用的是 `poseidon-solidity` 库自带的预编译字节码，外面套了一层适配合约，每次哈希多一次调用，所以直接集成会再便宜一些。这个库自己声明未经审计，运行时字节码 23,478 字节（上限 24,576），按本项目的编译设置编出来会超过上限。它只是为这次实测临时安装的，没有加入依赖。

*完整操作，本地实测（2026-10-13，`contracts/test/track-b/variant-1/B1NoteToken.ts`）：深度 24，circomlibjs 的 Poseidon。*

| 操作 | gas |
| --- | --- |
| 铸造 | 1,375k |
| note 转账 | 1,370k |
| 销毁 | 1,376k |
| wrap，经家族 Wrapper | 1,403k |
| unwrap，经家族 Wrapper | 1,415k |

- A.1 的转账稳态是 467k，账户首次花费是 706k。
- 一笔转账的 1,370k 里，承诺树占 943k。其余 427k 是 21 个公开输入的 Groth16 验证、两个新的作废符存储槽、calldata、事件，以及指向上一次操作的链接。
- 对一棵全新的树做第一次操作要多花约 45.5 万（第一次铸造是 1,830k）。某个代币第一次 wrap 时还要部署它的包装 ERC-20（1,998k）。
- 换成手工优化的 Poseidon，承诺树是 696k，一次操作约 112 万。这个没有做（§14 D8）。
- 深度 32 时，一次操作要多花约 30 万。
- 运行时字节码：`B1NoteToken` 15,104 字节，验证器 4,454 字节（上限 24,576）。

**其它限制。**

| 限制 | 说明 |
| --- | --- |
| 证明时间 | 在 Node 里实测约 2.9 秒，含见证计算和证明（2026-10-13，开发用的可信设置）；A.1 是 1.3 到 1.5 秒。证明密钥 25.8 MB（A.1 的 transfer 是 15.0 MB） |
| 提交者可见 | Alice 自己提交付款，会暴露她的地址在那一刻做了一笔隐私交易。要隐藏需要代发服务和手续费机制，不在 0.1 范围内 |
| 扫描量随代币增长，而不是随用户增长 | 每个钱包都要处理每一笔交易。交易多的代币需要索引服务 |
| 监管视图无法收窄到一把公钥 | §6.2 |
| 每笔交易两个输入 | 余额零碎时要先合并 |
| 进出是公开的 | 铸造、销毁、wrap、unwrap 的金额和公开地址可见 |

## 13. 0.1 的范围

包含：join-split 电路、角色铸造、Wrapper 端口、监管 memo、上面的事件与视图，以及一个在浏览器里扫描、保存 note 并生成证明的客户端。

不包含：公开账本模块、`prepare` / `cancel`、代发服务、独立的只读密钥、批量插入树、两个以上的输入。

0.2 的范围相同。它只改表面（见文首的说明）。

0.3 在核心里加入初始发行和销毁，并把角色铸造改名为可增发。电路不变。0.3.0 的部署表单要先证明初始发行，再发送部署交易。
