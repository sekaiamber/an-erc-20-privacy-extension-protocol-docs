# 06 架构草案

状态：`Draft`

> 本文是一个用来组织讨论的**初始草案**，尚未做出技术路线选择。所有组件的具体实现方式都可能改变。

## 总览

```
┌──────────────────────────────────────────────────────────┐
│                     Privacy-Extended Token                │
│                                                          │
│   ┌────────────────────┐        ┌─────────────────────┐  │
│   │   Public Ledger    │ shield │   Private Ledger    │  │
│   │   (标准 ERC-20)     │ ─────► │   (隐私状态)          │  │

                     ▲

            ┌────────┴────────┐

            │ (钱包 / 浏览器)  │
            └─────────────────┘
```

## 组件

### 1. Public Ledger

- 标准 ERC-20 实现，对外接口不变。
- 额外持有一个"隐私池托管余额"，等于所有已 shield 但未 unshield 的代币总量，以满足总量守恒（G4）。

### 2. Private Ledger

维护隐私状态。候选形态：

- **note 模型**：承诺集合（增量 Merkle 树）+ nullifier 集合。
- **加密账户模型**：`address => 密文余额`。

两者的对比见 [03 方案全景](03-landscape.md)。

### 3. Verifier

- 验证隐私操作合法性的合约。
- ZK 路线下是证明验证合约；FHE 路线下是密文运算与解密回调的接口。

### 4. Client / SDK

- 管理用户的隐私密钥（花费密钥、查看密钥）。
- 扫描链上事件发现属于自己的 note 或密文更新。
- 生成证明或密文。

## 操作流程（note 模型为例）

| 操作 | 公开输入 | 私密输入 | 效果 |
| --- | --- | --- | --- |
| shield | 金额、新承诺 | note 随机数 | 公开余额减少，承诺插入树 |
| transfer | 树根、nullifier、新承诺 | 输入 note、路径、输出 note | 消耗输入 note，产生输出 note |
| unshield | 树根、nullifier、金额、接收地址 | 输入 note、路径 | 消耗 note，公开余额增加 |

## 扩展点

- **合规钩子**：在 unshield 路径上可选地验证关联集合证明。
- **查看密钥**：note 加密时附带对查看密钥的加密副本。
- **Gas 代付**：unshield 支持指定中继者费用。

## 待决问题

- [ ] 采用 note 模型还是加密账户模型？（决定 P2 / P3 的达成程度）
- [ ] 证明系统选择（Groth16 / PLONK / 其他）？
- [ ] 隐私状态是否与公开 ERC-20 在同一合约内，还是通过独立扩展合约挂接？
- [ ] 如何让已有的 ERC-20 代币（无法修改合约）接入？是否提供"包装"模式作为兜底？
- [ ] 升级策略。

每个待决问题解决后应形成一条 ADR。
