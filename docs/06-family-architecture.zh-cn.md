# 06 家族架构

状态：`Draft`

## 分层

协议家族分三层，每层回答一个不同受众的问题：

| 层 | 受众 | 回答的问题 | 载体 |
| --- | --- | --- | --- |
| **家族级约定** | 所有集成方与实现者 | 一个"隐私扩展 ERC-20"在链上长什么样，怎么调用 | [07 家族级约定](07-family-conventions.zh-cn.md) |
| **Track** | 钱包、DEX、浏览器等集成方；路线改变了用户或监管方必须知道的前提时，也包括他们 | 哪些东西一改就成了另一套系统：接口与账本语义、状态模型、信任基础 | `docs/tracks/track-x/README.md` |
| **Variant** | 最终用户与监管方 | 隐藏了什么、信任什么、密钥与证明由谁负责 | `docs/tracks/track-x/variant-n/` |

一条路线同时通过两项检验才是 Track（[ADR-0007](adr/0007-track-definition.zh-cn.md)）：

- **不可替代**：它的核心性质，无法在既有 Track 内靠新增一个 payload 类型、替换一个电路或增加一条客户端约定做到。
- **外部可见**：它改变了集成方、用户或监管方必须事先知道的前提。

任一项不通过的，是 Variant（要改合约或电路）或功能（不改合约）。Track A 与 Track B 的差别在集成方看到的东西：有没有公开账本，`balanceOf` / `transfer` 语义是什么。同一 Track 下的 Variant 对集成方表现一致，只在隐私保证与密码学内核上不同。Variant 之间自包含、互不依赖（ADR-0002）。

## 当前家族

```
Track A  双账本：公开账本（标准 ERC-20）+ 机密账本
  └─ A.1  twisted ElGamal 加密账户 + Groth16，账户 = 公钥          ← 主线，原型已跑通
家族工具  通用 Wrapper（10-wrapper）：为无公开账本的代币发行 wTOKEN 进 DeFi     ← 已部署（PEPWrapper）
家族工具  监管委员会（11）：门限监管密钥、成员、策略、审计                     ← 设计中（按项目部署）
Track B  纯机密：无公开账本
  └─ B.1  A.1 的机密账本去掉公开账本，mint / burn 金额公开          ← 原型已上 BSC testnet（0.2.0）
```

## 一个 Variant 的典型结构（以 A.1 为例）

```
┌──────────────────────────────────────────────────────────────┐
│  代币合约（一个地址）                                            │
│                                                              │
│  ┌──────────────────┐   0x03 shield    ┌────────────────────┐ │
│  │  公开账本          │ ───────────────► │  机密账本           │ │
│  │  OpenZeppelin ERC20│ ◄─────────────── │  id → {available,  │ │
│  │  balanceOf/transfer│   0x04 unshield  │   pending, folded, │ │
│  │  屏蔽代币托管于本合约│                  │   nonce}           │ │
│  └──────────────────┘                  └─────────┬──────────┘ │
│                                                  │ 0x01       │
│  ┌──────────────────┐   ┌──────────────┐   ┌──────▼─────────┐ │
│  │ A1Payload 解析    │   │ BabyJubjub   │   │ Groth16 验证合约 │ │
│  │ type/flags/段     │   │ 点加 / 窗口表 │   │ transfer/unshield│ │
│  └──────────────────┘   └──────────────┘   └────────────────┘ │
└──────────────────────────────────────────────────────────────┘
                     ▲ 标准 transfer / transferFrom 选择器 + 尾部 payload
        ┌────────────┴────────────┐              ┌──────────────┐
        │ 客户端 / 中继者           │              │ 监管方        │
        │ 密钥派生、加密、memo、证明 │              │ 解 memo、重建余额│
        └─────────────────────────┘              └──────────────┘
```

家族级约定规定的是最上面那条边（选择器 + payload）以及事件、密钥派生、监管接口；框内的一切属于 Variant。

## 演进规则

- 新增 Track：只在某条路线确实要推进时才开，字母不预先分配。需要家族级 ADR，写明它如何通过 ADR-0007 的两项检验，以及每个家族工具为支持它要做什么。
- 新增 Variant：在既有 Track 下新建目录，自带设计、规范、评估表；不需要家族级 ADR。
- 家族级约定的变更影响所有 Track，必须走 ADR 并给出迁移说明。
- 只有主线 Variant 有实现（ADR-0002 第 5 条）。
