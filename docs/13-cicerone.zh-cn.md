# 13 向导 Cicerone

状态：`Draft`（2026-10-14）。Cicerone 这个名字见 [ADR-0011](adr/0011-project-name-casata.zh-cn.md) 第 5 条。外观遵循 [12 视觉风格](12-visual-style.zh-cn.md)。

Cicerone 是 dApp 里把访客从「我想要一个隐私代币」带到部署页面的那一部分。本文说明它怎样决定问什么。它不给家族增加任何概念：它在其中做选择的，就是 [06](06-family-architecture.zh-cn.md) 和 [ADR-0008](adr/0008-modules.zh-cn.md) 里的 Track、Variant 和模块。

Cicerone 只讲解和推荐。它不持有密钥，不持有资金，也不自己部署任何东西：每一笔交易都由访客自己的钱包发出。

## 1. 流程

1. **开场白。** Cicerone 说明自己是谁、接下来怎么走。
2. **访客为什么来。** 第一对牌：发一个新代币，或者看看手上已有的代币。第二张通向一个地址输入框；代币的探测接口（`casata()`、`casataModules()`，[07 §13.3](07-family-conventions.zh-cn.md)）说明它属于哪个 Variant，随后打开那个 Variant 的页面。
3. **一对一对的牌。** 每一步给出一个问题和两张牌，一个答案一张。访客取一张。
4. **手牌。** 取走的牌以简短的形式进入页面底部的手牌。手牌按顺序显示到目前为止的每个回答。从手牌里点回一张，就回到那一步，之后的回答作废。
5. **推荐。** 只剩一个组合时，Cicerone 把它作为最后一张牌给出：Track、Variant、模块、隐藏了什么、代价是什么，以及准备部署的页面链接。

每个问题恰好两个答案。有三种结果的选择，拆成两个问题来问。

## 2. 树是推出来的，不是写出来的

Cicerone 不保存一棵问题树。它保存两份清单和一条规则，树由它们推出来。家族长大时，清单跟着长，树自己就变了。

### 2.1 组合目录

每个**已经实现、能在 dApp 里部署**的组合占一条：一个 Variant 加上它的一组模块。每条包括：

| 字段 | 含义 |
| --- | --- |
| Track、Variant | 与家族登记表一致 |
| 模块 | 这个组合带的模块 |
| 答案 | 对每个问题，这个组合代表哪个答案。某条没有回答的问题，对它来说两个答案都成立 |
| 部署 | dApp 里准备部署的页面，已选好这个组合 |

只有设计、或者 Variant 文档写着「没有实现或测试」的组合，不进目录。Cicerone 只推荐能部署的东西。

### 2.2 问题清单

一份有顺序的清单。每个问题有 id、层次和两个答案。每个答案定下一个 Track 或一个模块，它的牌上画的就是那个 Track 或模块的图标（§5）。按层次排序：

1. **Track**：关于状态模型的问题，例如收付双方是否隐藏。
2. **Variant**：区分同一 Track 下不同 Variant 的问题。
3. **模块**：区分同一 Variant 下不同组合的问题。

同一层次内，按加入的先后排。

### 2.3 规则

每一步，根据已经给出的回答：

1. **候选**是与每个已给回答都一致的目录条目。
2. 只剩**一个**候选，流程以它结束。
3. 否则，Cicerone 问**清单里第一个能把候选分开的问题**：有的候选代表这个答案，有的代表那个。所有候选答案都一样的问题跳过，因为回答它什么也不会改变。

有两个候选没有任何问题能分开，说明清单有错。dApp 加载目录时会检查这种情况，并在控制台报告。

### 2.4 由规则得出的结果

- 只有一个 Variant 的 Track，不问 Variant 的问题。
- 某个 Variant 不支持的模块，在只剩这个 Variant 时永远不会被问到，因为没有候选在这一点上不同。
- 所有组合答案都一样的问题，永远不会被问到。等有组合答得不一样时，它自己就出现了。
- 问题的先后就是层次的先后：Cicerone 先定 Track，再定 Variant，最后定模块。

## 3. 现在的目录

问题：

| Id | 层次 | 问题 | 答案 |
| --- | --- | --- | --- |
| `parties` | Track | 什么必须藏起来？ | 金额，以及谁付给谁的一切痕迹 / 金额，收付双方用化名（账户 id 由密钥算出，不由钱包地址算出，每次付款都不变） |
| `ledger` | 模块 | 钱包和 DeFi 在哪里接触这个代币？ | 在它自己的地址上（公开账本） / 只经过家族 Wrapper（只有机密账本） |
| `issuance` | 模块 | 部署之后，供应量还能增加吗？ | 不能：部署时发行多少，就只有多少（不带可增发） / 能：铸造者可以继续发行（可增发） |

目录：

| 组合 | 模块 | `parties` | `ledger` | `issuance` | 部署 |
| --- | --- | --- | --- | --- | --- |
| 带公开账本的 A.1，固定供应 | 公开账本 | 化名 | 在它自己的地址上 | 固定 | `/tracks/a/1/deploy?compose=L` |
| 带公开账本的 A.1，可增发 | 公开账本、可增发 | 化名 | 在它自己的地址上 | 可增发 | `/tracks/a/1/deploy?compose=LM` |
| 纯隐私的 A.1，固定供应 | Wrapper 端口 | 化名 | 经过 Wrapper | 固定 | `/tracks/a/1/deploy?compose=W` |
| 纯隐私的 A.1，可增发 | 可增发、Wrapper 端口 | 化名 | 经过 Wrapper | 可增发 | `/tracks/a/1/deploy?compose=MW` |
| B.1，固定供应 | Wrapper 端口 | 不留痕迹 | 经过 Wrapper | 固定 | `/tracks/b/1/deploy?compose=W` |
| B.1，可增发 | 可增发、Wrapper 端口 | 不留痕迹 | 经过 Wrapper | 可增发 | `/tracks/b/1/deploy?compose=MW` |

由此推出的流程：

```
发新币 ─┬─ 不留痕迹 ──────────────────────────┬─ 固定 ──── B.1，固定供应
        │                                     └─ 可增发 ── B.1，可增发
        └─ 化名 ─────┬─ 在它自己的地址上 ─────┬─ 固定 ──── 带公开账本的 A.1，固定供应
                     │                        └─ 可增发 ── 带公开账本的 A.1，可增发
                     └─ 经过 Wrapper ─────────┬─ 固定 ──── 纯隐私的 A.1，固定供应
                                              └─ 可增发 ── 纯隐私的 A.1，可增发
```

在 B.1 这一支，`ledger` 问题分不开任何候选（B.1 没有公开账本），所以那里不问它（§2）。

从 A.1 0.7.0 和 B.1 0.3.0 起，一个 Variant 的模块的任意子集都是代币（[ADR-0013](adr/0013-mintable.zh-cn.md)），发行方式成了一个选择，于是加了 `issuance` 问题（2026-10-15）。在此之前每个组合都带角色铸造，所以不问发行方式。目录里放的是只用一种方式接触钱包和 DeFi 的组合；其余组合（同时带公开账本和 Wrapper 端口，或两者都不带）也已实现，可以在部署页上选，已有 ERC-20 经家族网关做成的隐私版本也一样（[14](14-gateway.zh-cn.md)）。

## 4. 家族增加东西时

| 增加了什么 | Cicerone 要改什么 |
| --- | --- |
| 已有 Variant 的一个新组合 | 目录加一条。如果现有问题分不开它和相邻的组合，在模块层次加一个问题 |
| 一个 Variant | 把它的组合加进目录。如果它和别的 Variant 同属一个 Track，在 Variant 层次加一个能区分它们的问题 |
| 一个 Track | 它的组合；如果现有问题分不开它，在 Track 层次加一个问题 |
| 一个模块 | 在模块层次加一个问题，以及带这个模块的组合 |

目录和问题清单放在 dApp 里，紧挨着家族登记表（`dapp/lib/family/cicerone.ts`）。每个问题和答案的文字在 dApp 的翻译文件里。新的 Track 或模块还要有一个图标（§5），在登记表（`dapp/lib/family/registry.ts`）里设定。

## 5. 外观

牌遵循 [12](12-visual-style.zh-cn.md)：纸上的墨、双线、标题用 EB Garamond。

- **图标。** 每个 Track、每个模块都有一个图标，画法同 12 §5 的小版画。Variant 没有图标：在牌上它是写出来的，不是画出来的。现在：Track A 是钱袋，Track B 是面具；公开账本是天平，可增发是印章，Wrapper 端口是钥匙。把某个模块排除在外的答案有自己的图：固定供应是一只关上的箱子。第一对牌与家族无关，用羽毛笔（发新币）和放大镜（看看一个代币）。
- **一张牌**画成文艺复兴时期的塔罗牌（*tarocchi*，十五世纪的意大利纸牌）：竖长，双线边框，一个表示步数的罗马数字，这个答案所定下的东西的图标，以答案为标题，一句说明，一行这个答案的代价。
- **手牌**是页面底部呈扇形排开的小牌。
- **动效。** 每一步的两张牌翻转入场；取走的那张缩小飞进手牌；另一张淡出。指向手牌里的一张时，旁边的牌让开。这是页面本身唯一会动的地方（12 §2）。读者的系统要求减少动效时，牌只做淡入淡出。动效用 anime.js 编排，只改变 transform 和透明度。
- **合成大卡。** 走到最后，手牌一张张飞进一张大卡。Track 是牌上的人物，模块是它带的装备，没被问到的模块也在其中；Variant 和版本写在人物下面。大卡旁边是这个组合的数据和部署链接。此时手牌栏收起。数据下面是去路：部署按钮用封蜡红，这是强烈的行动召唤（12 §3）；旁边两个描边按钮，「退一步」和「重新开始」。
